# DriverPass (System Analysis and Design)


## Briefly summarize the DriverPass project. Who was the client? What type of system did they want you to design?
DriverPass was the client, a driver training company owned by Liam. They wanted a website-based system where customers can sign up for packages, use online lessons and practice tests, and book two-hour driving lessons. Staff also needed basic scheduling tools, different access levels, simple reports, and a way to track changes to reservations.

## What did you do particularly well?
I did well at writing down what the client wanted clearly and turning it into a design that fits how the business works day to day (customer accounts, scheduling lessons, practice tests, and basic staff/admin tasks). I also included security and different access levels, since that matters for how the system would be used.

## If you could choose one part of your work on these documents to revise, what would you pick? How would you improve it?
I would go back and clean up the nonfunctional requirements and technical requirements parts so they are easier to understand and less vague. For example, I would add simple details about speed, uptime, and security rules like password standards and lockout limits so it’s clearer what the system should meet.

## How did you interpret the user’s needs and implement them into your system design? Why is it so important to consider the user’s needs when designing?
I looked at what each type of user needs to do (customer, secretary, admin/IT, owner, driver) and made sure the design supports those basic tasks. For example, I focused on scheduling lessons without double-booking, keeping track of changes, and showing test progress. User needs matter because if the system doesn’t fit how people actually work, it will be harder to use and it won’t really help the business.

## How do you approach designing software? What techniques or strategies would you use in the future to analyze and design a system?
I usually start by gathering requirements and making sure I understand what the client wants. Then I use some basic diagrams, like use cases and simple UML's to check that the steps and data make sense. In the future, I’ll keep doing that, and I’ll make small updates based on feedback so I can catch issues before the system gets built.
